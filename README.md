# PushUp Tracker — Telegram-бот для учёта отжиманий

Бот обрабатывает Telegram-видеокружочки с помощью Google Gemini, хранит результаты в SQLite и автоматически публикует ежедневный итог. Показывает этапы обработки в Rich HTML-сообщении группы, позволяет автору исправить результат вручную или повторить анализ, поддерживает настройку доступа, админские корректировки и диагностику.

## Основные возможности

- Видеокружочки анализируются через Gemini API (`vision.py`), результаты сохраняются за дату исходного сообщения. На запрос каждой модели отведено до 45 секунд, включая внутренние повторные запросы SDK; при таймауте, HTTP 408/429/500/502/503/504 выполняется не более одного перехода на отличающуюся резервную модель. Общий таймаут групповой обработки (очередь, скачивание, анализ) — 240 секунд; обновление карточки ограничено 10 секундами. После ошибки обеих моделей карточка перестаёт анимироваться, сохраняет предыдущий результат (если есть) и возвращает доступные действия. Осиротевшие задачи восстанавливаются при плановой проверке и перезапуске.
- Для каждого кружочка бот создаёт отдельное **Rich HTML-сообщение** с заголовком, результатом и статусом **в очереди → скачивание → анализ → готово**. Во время скачивания и анализа движущийся индикатор обновляется примерно раз в секунду (с учётом ограничений Telegram) без фиктивных процентов готовности Gemini. Полоска из блоков `█` и `░` движется туда-обратно и отображается моноширинным шрифтом.
- Действия доступны только автору кружочка. После первой неудачной попытки доступна только кнопка повторного анализа без срока блокировки. После первого успешного результата или второй завершённой попытки (даже при ошибке) начинается фиксированное **15-минутное окно**. Ручной ввод появляется только после двух завершённых попыток; повторные действия не продлевают срок. Во время анализа кнопки скрыты. Прерванная перезапуском попытка не учитывается; автоматический переход на резервную модель относится к одной попытке.
- Кнопка ручного изменения запрашивает **целое неотрицательное число**. Оно **заменяет результат конкретного кружочка**, включая результат успешного автоматического анализа. Повторный анализ также заменяет результат; если он завершился ошибкой, предыдущий результат сохраняется.
- **Антинакрутка:** максимум **4 уникальных кружочка с ручным вводом в сутки на участника в каждом чате** (сутки по `REPORT_TIMEZONE`), максимум **3 ошибочных ответа на один запрос**. После трёх ошибок ручной ввод для этого кружочка блокируется; повторное нажатие кнопки или анализ не сбрасывают ошибки ожидающего запроса. Повторная правка того же кружочка не расходует дополнительную квоту. Автоматически распознанные кружочки без ручных правок в квоту не входят; повторный анализ уже исправленного вручную кружочка не возвращает израсходованную квоту.
- Числа выше внутреннего порога отклоняются **без раскрытия порога участнику**. При первой попытке превышения по кружочку бот отправляет владельцу уведомление, попытки фиксируются для `/debug`; высокие ручные результаты засчитываются, но владелец получает уведомление для проверки. Подтверждения владельца для самого зачёта не требуется.
- Ручной ввод учитывается только при ответе на сообщение-запрос или исходный кружочек и только от его автора. Для следующего изменения нужно снова нажать кнопку. Строки, SQL, Unicode-цифры, дроби и отрицательные числа не принимаются.
- **`/me`** — личное количество отжиманий с начала текущей календарной недели (понедельник) и месяца, включая сегодня и корректировки владельца.
- **Дубликаты кружочков:** в рамках группы проверяются Telegram `file_unique_id`, `file_id` и SHA-256 скачанного видео. Подтверждённый дубликат не передаётся Gemini и не засчитывается; автор получает пятикратную обычную норму на дату отправки дубликата. Повторные нарушения в тот же день не умножают норму. Если норма ×5 не выполнена, итоговый отчёт сразу назначает денежный штраф `CASH_FINE`, без дополнительной штрафной нормы на следующий день. При выполнении ×5 денежного штрафа нет. Повторный анализ исходного сообщения разрешён по прежним правилам. Старые кружочки проверяются по сохранённому `file_id`; их SHA-256 и `file_unique_id` не восстанавливаются автоматически. Перекодированные копии с другими идентификаторами и хешем не гарантированно обнаруживаются.
- **`/stats` и `/today`** показывают только количество отжиманий за текущий день, включая нули для участников с предыдущими результатами. Штрафы и статусы выполнения в этих командах не отображаются.
- **`/yesterday`** показывает подробные итоги закрытого предыдущего дня, выполнение норм, ручной ввод и назначенные штрафы.
- Автоотчёт за вчера публикуется в `00:00` в часовом поясе `REPORT_TIMEZONE`.
- Если бот был выключен в полночь, при запуске он обрабатывает накопившиеся обновления Telegram и затем отправляет пропущенный отчёт за вчера. Кружочки сохраняют исходную дату отправки.
- **`/debug`** доступен только `OWNER_ID` и только в личных сообщениях: состояние SQLite, статистика ручных вводов, последние пять попыток превысить внутренний порог, последние пять высоких ручных результатов, число записей/групп, модели и следующий отчёт. Токены и ключи не выводятся.
- Админские команды в `/help` и Telegram-меню команд не публикуются.

## Правила штрафов

1. До первого сохранённого результата, админской корректировки или подтверждённого дубликата участник не учитывается для штрафов. В дальнейшем отсутствие результатов в какой-либо день считается нулём.
2. В течение текущего дня никто не штрафуется *за нехватку отжиманий именно сегодня*: этот день ещё не закрыт.
3. Если итог ниже действующей личной нормы, на **следующий** день назначается обычная норма **закрытого дня** × 2 + 10. Например, при норме 30 бот назначит 70. Назначение сохранит это значение и при повышении обычной нормы на следующий день.
4. Если штрафная норма не выполнена, на следующие сутки снова 210, без накопления штрафа. Если выполнена — последующие сутки снова обычная норма.
5. Для дня с подтверждённым дубликатом вместо обычной схемы действует норма ×5 или денежный штраф `CASH_FINE` по итогам дня. На следующий день действует обычная норма, если нет нового нарушения.
6. Исторические корректировки владельца пересчитывают цели в будущих отчётах. Уже отправленные сообщения автоматически не редактируются.

**Пограничный случай полуночи:** если первый успешный результат или вторая завершённая попытка получены в 23:59:00, изменение результата и запуск повторного анализа доступны до 00:14:00 (не включая этот момент). Ручная правка и результат повторного анализа относятся к дате исходного кружочка, даже если обработка завершилась после полуночи. Поэтому уже отправленный в 00:00 отчёт может устареть; `/yesterday` пересчитает данные при следующем запросе. Для окончательной фиксации дня владелец может применить `/setpushups`.

## Пользовательские команды

| Команда | Назначение |
|---|---|
| `/start` | Краткая информация о боте; в группе регистрация чата |
| `/help` | Все доступные обычным участникам команды, без админских |
| `/stats`, `/today` | Короткая статистика: отжимания за сегодня |
| `/yesterday` | Подробные итоги за вчера, штрафы по завершённому дню |
| `/me` | Мои отжимания за текущую неделю и месяц (в группе) |
| `/rules` | Правила из `rules.txt` |
| `/myid` | Твой Telegram ID (только в личке) |

Бот принимает видеокружочки (`video_note`) в разрешённых группах. После завершения анализа автор выбирает действие внутри Rich HTML-сообщения. При нажатии **«Изменить результат»** бот отвечает на исходный кружочек сообщением `ForceReply` с запросом числа; принятый ручной результат помечается ✍️. При ошибке первого анализа сначала нужно повторить анализ; ручной ввод открывается после второй завершённой попытки.

Карточка использует нативный формат Telegram Rich Messages: заголовки, текстовый индикатор активности и встроенные действия. Произвольные CSS/JavaScript в этом формате не выполняются; отдельный HTML-файл не отправляется. Для карточки не используется внешняя inline-клавиатура. Отправкой через `sendRichMessage` с `rich_message.html` и обновлением через `editMessageText` с `rich_message` управляет модуль `rich_messages.py`, совместимый с закреплённой версией aiogram.

Число выше внутреннего порога не записывается; ответ пользователю не сообщает порог и совпадает с сообщением о некорректном формате. Для реального результата выше порога участник может повторить анализ в доступное время, отправить новое видео или обратиться к владельцу для `/setpushups`. При исчерпании ручной квоты также доступны видеораспознавание и админская корректировка. В личке видео анализируется отдельно для диагностики: бот отправляет текстовый отчёт без записи в статистику.

Время окончания действий указано в карточке. По истечении срока карточка сворачивается до итогового количества отжиманий (или «не засчитано», если результата нет). Кнопки и служебные сведения удаляются проверкой каждые 10 секунд; сервер проверяет срок при каждом действии, а поздний результат повторного анализа не сохраняется. Данные карточки сохраняются в SQLite. Если бот перезапустился во время обработки, карточка сообщает о прерывании и позволяет автору запустить анализ заново в пределах доступного срока, если он уже начался. После обновления и перезапуска существующие активные карточки переводятся в Rich HTML. Для новых кружочков карточки создаются сразу; старые результаты без карточек автоматически ими не дополняются.

## Команды владельца

Команды управления доступом работают **только в личке `OWNER_ID`**:

| Команда | Назначение |
|---|---|
| `/access` | Разрешённые группы и пользователи |
| `/allowgroup CHAT_ID` | Разрешить группу |
| `/denygroup CHAT_ID` | Запретить группу и выйти |
| `/allowuser USER_ID` | Разрешить личные сообщения |
| `/denyuser USER_ID` | Запретить личные сообщения |
| `/debug` | Полная диагностика в личке владельца; в группе — безопасная диагностика норм и штрафов, доступная участникам |

Дневные корректировки выполняются **только владельцем**, в том числе в разрешённой группе:

```text
# В группе в ответ на сообщение участника:
/setpushups 150 [YYYY-MM-DD]
/clearpushups [YYYY-MM-DD]

# В группе по User ID:
/setpushups USER_ID 150 [YYYY-MM-DD]
/clearpushups USER_ID [YYYY-MM-DD]

# В личке владельца:
/setpushups CHAT_ID USER_ID 150 [YYYY-MM-DD]
/clearpushups CHAT_ID USER_ID [YYYY-MM-DD]
```

`/setpushups` задаёт **итог**, а не прибавляет число к видео. Допустимы целые числа `0..100000`. Если дата не указана, используется сегодняшний день по `REPORT_TIMEZONE`. Данные исходных видео не удаляются; `/clearpushups` отменяет переопределение. Если пользователь не найден в базе, бот попытается получить его имя из Telegram.

### Управление штрафами в группе

- `/debug` — текущая базовая норма, история норм, штрафники и прогресс каждого участника. В группе не показываются ключи, системные данные или сведения о других группах.
- `/penalty off all [YYYY-MM-DD]` — отключить штрафы для всех на выбранный день. Дубликаты остаются незасчитанными.
- `/penalty on USER_ID [YYYY-MM-DD]` — принудительная штрафная норма (обычная норма предыдущего дня ×2 + 10); если есть дубликат, действует ×5.
- `/penalty auto all [YYYY-MM-DD]` — вернуть автоматический расчёт всей группе.
- `/penalty off`, `/penalty on`, `/penalty auto` — ответом на сообщение участника; можно указать USER_ID вместо ответа. Дата по умолчанию сегодня по REPORT_TIMEZONE.
- `/settarget 30 2026-11-24` — исправить историческую базовую норму с указанной прошедшей даты до следующего изменения. История общая для всех групп, текущая норма не меняется.

Изменять настройки могут только OWNER_ID. Режимы штрафов сохраняются в SQLite в `penalty_overrides`. Индивидуальная настройка приоритетнее групповой; команда с `all` сбрасывает индивидуальные настройки на выбранный день. Отключение снимает и обычную штрафную норму, и штраф ×5, включая новые дубликаты этого дня; обычную норму всё равно нужно выполнить. На следующий день вновь действуют автоматические правила (если нет отдельной настройки). Уже опубликованные отчёты не редактируются; /yesterday пересчитывает итог. Ни одна команда не удаляет видео или историю нарушений.

## Установка

Для установки и обновления на сервере достаточно Docker с Compose.

```bash
git clone https://github.com/exname69/pushup-tracker.git
cd pushup-tracker
cp .env.template .env
# Отредактируй .env, укажи токен, Gemini API ключ, OWNER_ID и белые списки
sudo docker compose up -d --build
sudo docker compose logs -f --tail=100 bot
```

Пример основных параметров `.env`:

```dotenv
BOT_TOKEN=YOUR_TELEGRAM_BOT_TOKEN
GEMINI_API_KEY=YOUR_GEMINI_API_KEY
GEMINI_MODEL=gemini-3.5-flash-lite
GEMINI_FALLBACK_MODEL=gemini-3.5-flash-lite
REPORT_TIMEZONE=Europe/Zurich
DAILY_TARGET=100
CASH_FINE=500
DB_PATH=./data/pushups.sqlite3
OWNER_ID=123456789
ALLOWED_CHAT_IDS=-1001234567890
ALLOWED_USER_IDS=111111111,222222222
```

Переменная `GEMINI_FALLBACK_MODEL` задаёт резервную модель (по умолчанию модель диагностики). Если она совпадает с основной, повторного запроса к той же модели нет. Переменные `GEMINI_MODEL`, `REPORT_TIMEZONE`, `DAILY_TARGET`, `CASH_FINE`, `DB_PATH`, `OWNER_ID`, `ALLOWED_CHAT_IDS`, `ALLOWED_USER_IDS` описывают используемые модель, дату отчёта, норму, денежный штраф в правилах, SQLite, владельца и белые списки. Не добавляйте `.env` в Git. `rules.txt` перечитывается при каждом запросе; поддерживает `{DAILY_TARGET}`, `{PENALTY_TARGET}`, `{REPORT_TIMEZONE}`, `{CASH_FINE}`. Путь можно переопределить переменной `RULES_PATH`.

Для работы бота в группах при необходимости отключите Privacy Mode в BotFather (`/setprivacy` → `Disable`). Группа должна быть в `ALLOWED_CHAT_IDS` или разрешена через `/allowgroup`. Бот покидает другие группы. Белые списки из SQLite имеют приоритет над `.env`.

## Хранение и миграция

В Compose рабочая база находится в `./data/pushups.sqlite3` на сервере и в `/app/data/pushups.sqlite3` внутри контейнера. Параметр `DB_PATH` в `.env` задаёт путь при запуске Python вне Compose.

В `daily_targets` хранится обычная норма с датой вступления в силу для всех групп бота. При изменении `DAILY_TARGET` бот записывает новую норму на дату запуска в `REPORT_TIMEZONE`. Предыдущие дни сохраняют свои нормы. До самой ранней известной даты применяется самая ранняя известная норма.

Таблицы базы включают `chats`, `members`, `video_counts`, `video_jobs`, `daily_overrides`, `daily_targets`, `reports`, `pending_manual`, `access_rules`, `manual_rejections`, `video_fingerprints` и `duplicate_videos`. Миграция создаёт недостающие таблицы и колонки. В `video_counts` поле `is_manual` обозначает текущий ручной результат, а `was_manual` сохраняет расход ручной квоты даже после повторного автоматического анализа. В `pending_manual` хранятся срок `expires_at_utc` и счётчик `invalid_attempts`.

Таблица `video_jobs` хранит Telegram file ID, автора, дату исходного кружочка, топик группы, ID карточки, состояние обработки, число завершённых попыток и фиксированный срок действий. Это позволяет повторно скачать видео и восстановить карточку после перезапуска. Сами видео постоянно на диске не сохраняются.

В журнале превышений хранятся только числовые попытки выше внутреннего порога (до 18 цифр), время, ID группы/пользователя/кружочка; произвольный текст ответа не сохраняется. Записи журнала старше 90 дней удаляются плановой очисткой.

**Старые ожидающие ручного ввода запросы без срока действия намеренно считаются просроченными.** У уже созданных запросов сохраняется записанный срок. Существующие результаты, чаты и корректировки не удаляются. При миграции старой схемы известный факт обработки считается одной завершённой попыткой, так как число попыток раньше не хранилось. Открытые окна с результатом сокращаются с 30 до 15 минут, а незакрытые кружочки без результата снова доступны для повторного анализа без таймера. Уже закрытые исторические карточки не открываются заново. Старые ручные результаты выше внутреннего порога сохраняются; новые ограничения применяются только к новым попыткам. Старые просроченные запросы очищаются при плановой уборке или первом ответе на них. Для резервного копирования работающей базы используйте SQLite backup, который учитывает записи в журнале WAL.

## Обновление

Если работающий бот использует файл `./data/pushups.sqlite3` на сервере, обновляйтесь из того же каталога проекта обычными командами. Если прежний путь другой или неизвестен, при первой выкладке используйте разовый перенос ниже.

```bash
git pull --ff-only
sudo docker compose up -d --build
```

Compose заменяет контейнер и подключает ту же папку `./data`. Изменение `DAILY_TARGET` вступает в силу с даты запуска. Для старой установки этой группы Compose передаёт известную историю — 30 до 24.11.2026 включительно и 40 с 25.11.2026. Собственную историю можно задать в `.env` через `DAILY_TARGET_HISTORY`. Для новой группы в шаблоне она пустая.

### Разовый перенос старой базы

Если прежний бот писал, например, в `/app/pushups.sqlite3`, файл находится внутри старого контейнера. После получения нового кода и **до удаления или пересоздания этого контейнера** выполните

```bash
sudo python3 scripts/migrate_legacy_db.py && sudo docker compose up -d --build
```

Команда сама проверяет путь. Если файл уже подключён из нужной папки, проверка завершается сразу. Иначе перенос останавливает прежний экземпляр и создаёт в `data/` проверенную копию с учётом журнала SQLite. При конфликте двух баз сохраняются обе, а ранее запущенный контейнер возобновляет работу. Для перехода с запуска без Docker остановите прежний процесс и укажите его файл через `--source-db /путь/к/старой.sqlite3`.

Полная сборка и запуск Telegram-бота требуют зависимостей из `requirements.txt`. Одновременно должен работать один экземпляр polling-бота.

В Docker-образ должны попадать все Python-модули, включая `tracker_core.py`, `video_workflow.py` и `rich_messages.py`; актуальный `Dockerfile` копирует их при сборке. Лимит обычного текстового Telegram-сообщения — 4096 символов. Результаты приватного видеоанализа никогда не попадают в групповую статистику.
