# PushUp Tracker — Telegram-бот для учёта отжиманий

Бот обрабатывает Telegram-видеокружочки с помощью Google Gemini, хранит результаты в SQLite и автоматически публикует ежедневный итог. Показывает этапы обработки в Rich HTML-сообщении группы, позволяет автору исправить результат вручную или повторить анализ, поддерживает настройку доступа, админские корректировки и диагностику.

## Основные возможности

- Видеокружочки анализируются через Gemini API (`vision.py`), результаты сохраняются за дату исходного сообщения.
- Для каждого кружочка бот создаёт отдельное **Rich HTML-сообщение** с заголовком, результатом и статусом **в очереди → скачивание → анализ → готово**. Во время скачивания и анализа движущийся индикатор обновляется примерно раз в 5 секунд без фиктивных процентов готовности Gemini.
- Действия **«Изменить результат»** и **«Обработать заново»** встроены в Rich HTML-сообщение. Они доступны только автору кружочка в течение **30 минут с первого результата или сообщения об ошибке**. Повторные действия не продлевают этот срок. Во время обработки действия для того же кружочка временно недоступны. Ручной ввод открывается только после первой завершённой попытки обработки (успешной или с ошибкой). Если бот перезапустился до её завершения, доступен только повторный анализ.
- Кнопка ручного изменения запрашивает **целое неотрицательное число**. Оно **заменяет результат конкретного кружочка**, включая результат успешного автоматического анализа. Повторный анализ также заменяет результат; если он завершился ошибкой, предыдущий результат сохраняется.
- **Антинакрутка:** максимум **4 уникальных кружочка с ручным вводом в сутки на участника в каждом чате** (сутки по `REPORT_TIMEZONE`), максимум **3 ошибочных ответа на один запрос**. После трёх ошибок ручной ввод для этого кружочка блокируется; повторное нажатие кнопки или анализ не сбрасывают ошибки ожидающего запроса. Повторная правка того же кружочка не расходует дополнительную квоту. Автоматически распознанные кружочки без ручных правок в квоту не входят; повторный анализ уже исправленного вручную кружочка не возвращает израсходованную квоту.
- Числа выше внутреннего порога отклоняются **без раскрытия порога участнику**. При первой попытке превышения по кружочку бот отправляет владельцу уведомление, попытки фиксируются для `/debug`; высокие ручные результаты засчитываются, но владелец получает уведомление для проверки. Подтверждения владельца для самого зачёта не требуется.
- Ручной ввод учитывается только при ответе на сообщение-запрос или исходный кружочек и только от его автора. Для следующего изменения нужно снова нажать кнопку. Строки, SQL, Unicode-цифры, дроби и отрицательные числа не принимаются.
- **`/stats` и `/today`** показывают только количество отжиманий за текущий день, включая нули для участников с предыдущими результатами. Штрафы и статусы выполнения в этих командах не отображаются.
- **`/yesterday`** показывает подробные итоги закрытого предыдущего дня, выполнение норм, ручной ввод и назначенные штрафы.
- Автоотчёт за вчера публикуется в `00:00` в часовом поясе `REPORT_TIMEZONE`.
- **`/debug`** доступен только `OWNER_ID` и только в личных сообщениях: состояние SQLite, статистика ручных вводов, последние пять попыток превысить внутренний порог, последние пять высоких ручных результатов, число записей/групп, модели и следующий отчёт. Токены и ключи не выводятся.
- Админские команды в `/help` и Telegram-меню команд не публикуются.

## Правила штрафов

1. До первого сохранённого результата или админской корректировки участник не учитывается для штрафов. В дальнейшем отсутствие результатов в какой-либо день считается нулём.
2. В течение текущего дня никто не штрафуется *за нехватку отжиманий именно сегодня*: этот день ещё не закрыт.
3. После завершения дня, если его итог ниже действующей нормы, на **следующий** день назначается `DAILY_TARGET × 2 + 10` (например, при норме 100 — 210).
4. Если штрафная норма не выполнена, на следующие сутки снова 210, без накопления штрафа. Если выполнена — последующие сутки снова обычная норма.
5. Исторические корректировки владельца пересчитывают цели в будущих отчётах. Уже отправленные сообщения автоматически не редактируются.

**Пограничный случай полуночи:** если первый результат или сообщение об ошибке получены в 23:59:00, изменение результата и запуск повторного анализа доступны до 00:29:00 (не включая этот момент). Ручная правка и результат повторного анализа относятся к дате исходного кружочка, даже если обработка завершилась после полуночи. Поэтому уже отправленный в 00:00 отчёт может устареть; `/yesterday` пересчитает данные при следующем запросе. Для окончательной фиксации дня владелец может применить `/setpushups`.

## Пользовательские команды

| Команда | Назначение |
|---|---|
| `/start` | Краткая информация о боте; в группе регистрация чата |
| `/help` | Все доступные обычным участникам команды, без админских |
| `/stats`, `/today` | Короткая статистика: отжимания за сегодня |
| `/yesterday` | Подробные итоги за вчера, штрафы по завершённому дню |
| `/rules` | Правила из `rules.txt` |
| `/myid` | Твой Telegram ID (только в личке) |

Бот принимает видеокружочки (`video_note`) в разрешённых группах. После завершения анализа автор выбирает действие внутри Rich HTML-сообщения. При нажатии **«Изменить результат»** бот отвечает на исходный кружочек сообщением `ForceReply` с запросом числа; принятый ручной результат помечается ✍️. При ошибке анализа ручной ввод также открывается этой кнопкой.

Карточка использует нативный формат Telegram Rich Messages: заголовки, текстовый индикатор активности и встроенные действия. Произвольные CSS/JavaScript в этом формате не выполняются; отдельный HTML-файл не отправляется. Для карточки не используется внешняя inline-клавиатура. Отправкой через `sendRichMessage` с `rich_message.html` и обновлением через `editMessageText` с `rich_message` управляет модуль `rich_messages.py`, совместимый с закреплённой версией aiogram.

Число выше внутреннего порога не записывается; ответ пользователю не сообщает порог и совпадает с сообщением о некорректном формате. Для реального результата выше порога участник может повторить анализ в доступное время, отправить новое видео или обратиться к владельцу для `/setpushups`. При исчерпании ручной квоты также доступны видеораспознавание и админская корректировка. В личке видео анализируется отдельно для диагностики: бот отправляет текстовый отчёт без записи в статистику.

Время окончания действий указано в карточке. По истечении срока действия убираются плановой проверкой раз в минуту; сам срок проверяется при каждом нажатии и ручном ответе, поэтому оставшаяся на экране кнопка не позволяет его продлить. Данные карточки сохраняются в SQLite. Если бот перезапустился во время обработки, карточка сообщает о прерывании и позволяет автору запустить анализ заново в пределах доступного срока. После обновления и перезапуска существующие активные карточки переводятся в Rich HTML. Для новых кружочков карточки создаются сразу; старые результаты без карточек автоматически ими не дополняются.

## Команды владельца

Команды управления доступом работают **только в личке `OWNER_ID`**:

| Команда | Назначение |
|---|---|
| `/access` | Разрешённые группы и пользователи |
| `/allowgroup CHAT_ID` | Разрешить группу |
| `/denygroup CHAT_ID` | Запретить группу и выйти |
| `/allowuser USER_ID` | Разрешить личные сообщения |
| `/denyuser USER_ID` | Запретить личные сообщения |
| `/debug` | Сводная диагностика состояния бота (только в личке) |

Дневные корректировки выполняются **только владельцем**, в том числе в разрешённой группе:

```text
# В группе в ответ на сообщение участника:
/setpushups 150 [YYYY-MM-DD]
/clearpushups [YYYY-MM-DD]

# В группе по User ID:
/setpushups USER_ID 150 [YYYY-MM-DD]
/clearpushups USER_ID [YYYY-MM-DD]

# В личке владельца:
/setpushups CHAT_ID USER_ID 150 [YYYY-MM-DD]
/clearpushups CHAT_ID USER_ID [YYYY-MM-DD]
```

`/setpushups` задаёт **итог**, а не прибавляет число к видео. Допустимы целые числа `0..100000`. Если дата не указана, используется сегодняшний день по `REPORT_TIMEZONE`. Данные исходных видео не удаляются; `/clearpushups` отменяет переопределение. Если пользователь не найден в базе, бот попытается получить его имя из Telegram.

## Установка

Требуется сервер с Docker и Docker Compose. Существующий `compose.yaml` можно оставить без изменений.

```bash
git clone https://github.com/exname69/pushup-tracker.git
cd pushup-tracker
cp .env.template .env
# Отредактируй .env, укажи токен, Gemini API ключ, OWNER_ID и белые списки
sudo docker compose up -d --build
sudo docker compose logs -f --tail=100 bot
```

Пример основных параметров `.env`:

```dotenv
BOT_TOKEN=YOUR_TELEGRAM_BOT_TOKEN
GEMINI_API_KEY=YOUR_GEMINI_API_KEY
GEMINI_MODEL=gemini-3.5-flash-lite
REPORT_TIMEZONE=Europe/Zurich
DAILY_TARGET=100
CASH_FINE=500
DB_PATH=./data/pushups.sqlite3
OWNER_ID=123456789
ALLOWED_CHAT_IDS=-1001234567890
ALLOWED_USER_IDS=111111111,222222222
```

Переменные `GEMINI_MODEL`, `REPORT_TIMEZONE`, `DAILY_TARGET`, `CASH_FINE`, `DB_PATH`, `OWNER_ID`, `ALLOWED_CHAT_IDS`, `ALLOWED_USER_IDS` описывают используемые модель, дату отчёта, норму, денежный штраф в правилах, SQLite, владельца и белые списки. Не добавляйте `.env` в Git. `rules.txt` перечитывается при каждом запросе; поддерживает `{DAILY_TARGET}`, `{PENALTY_TARGET}`, `{REPORT_TIMEZONE}`, `{CASH_FINE}`. Путь можно переопределить переменной `RULES_PATH`.

Для работы бота в группах при необходимости отключите Privacy Mode в BotFather (`/setprivacy` → `Disable`). Группа должна быть в `ALLOWED_CHAT_IDS` или разрешена через `/allowgroup`. Бот покидает другие группы. Белые списки из SQLite имеют приоритет над `.env`.

## Хранение и миграция

Таблицы: `chats`, `members`, `video_counts`, `video_jobs`, `daily_overrides`, `reports`, `pending_manual`, `access_rules`, `manual_rejections`. Миграция создаёт недостающие таблицы и колонки. В `video_counts` поле `is_manual` обозначает текущий ручной результат, а `was_manual` сохраняет факт расхода ручной квоты даже после повторного автоматического анализа. В `pending_manual` хранятся срок `expires_at_utc` и счётчик `invalid_attempts`.

Таблица `video_jobs` хранит Telegram file ID, автора, дату исходного кружочка, топик группы, ID карточки, состояние обработки, факт завершения первой попытки и фиксированный срок действий. Это позволяет повторно скачать видео и восстановить карточку после перезапуска. Сами видео постоянно на диске не сохраняются.

В журнале превышений хранятся только числовые попытки выше внутреннего порога (до 18 цифр), время, ID группы/пользователя/кружочка; произвольный текст ответа не сохраняется. Записи журнала старше 90 дней удаляются плановой очисткой.

**Старые ожидающие ручного ввода запросы без срока действия намеренно считаются просроченными.** У уже созданных запросов сохраняется записанный срок. Существующие результаты, чаты и корректировки не удаляются. Старые ручные результаты выше внутреннего порога сохраняются; новые ограничения применяются только к новым попыткам. Старые просроченные запросы очищаются при плановой уборке или первом ответе на них. Для обновления сделайте SQLite backup и сохраните Docker volume с `data/`. Для активной БД с WAL используйте штатный SQLite backup, а не копирование одного `.sqlite3`.

## Обновление

Положите все файлы обновления в корень клона, сохранив пути, затем пересоберите образ и перезапустите бота.

```bash
sudo docker compose build bot
sudo docker compose up -d --no-deps --force-recreate --no-build bot
sudo docker compose logs -f --tail=100 bot
```

Полная сборка и запуск Telegram-бота требуют зависимостей из `requirements.txt`. Убедитесь, что одновременно работает только один экземпляр polling-бота.

В Docker-образ должны попадать все Python-модули, включая `tracker_core.py`, `video_workflow.py` и `rich_messages.py`; актуальный `Dockerfile` копирует их при сборке. Лимит обычного текстового Telegram-сообщения — 4096 символов. Результаты приватного видеоанализа никогда не попадают в групповую статистику.
