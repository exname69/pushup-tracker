# PushUp Tracker — Telegram-бот для отжиманий

Telegram-бот для ежедневного челленджа по отжиманиям. Принимает видеокружочки (`video_note`), анализирует их через **Google Gemini Video API** и сохраняет результаты в SQLite.

При неудачном анализе или ответе Gemini с `uncertain=true` бот предлагает автору указать количество отжиманий вручную. Такие результаты помечаются ✍️. Владелец бота может отдельно скорректировать **дневной итог конкретного участника**.

Каждый день в **00:00** по настроенному часовому поясу бот публикует отчёт **за предыдущий день**. При невыполнении нормы на следующие сутки назначается штрафная норма. Рейтингов и соревнований нет.

Дополнительные возможности:

- Белые списки Telegram-групп и пользователей, с управлением через команды владельца.
- Автоматический выход из неразрешённых групп.
- Debug-анализ кружочков в личке **без записи в статистику**.
- Отдельная модель Gemini для debug-режима.
- Ручная корректировка дневного итога участника без изменения результатов исходных видео.
- Правила челленджа из файла `rules.txt`.

## Сервер

Пример конфигурации VPS:

- **OS:** Ubuntu 24.04 LTS
- **CPU:** 2 vCPU
- **RAM:** 2 GB
- **SSD:** 40 GB
- **Swap:** 1 GB

Приложение запускается через Docker Compose. Анализ видео выполняет облачный Gemini API; локальный MediaPipe/pose-детектор не используется.

## Установка и запуск

### 1. Установка Docker

```bash
sudo apt update
sudo apt install -y docker.io docker-compose-v2 git
sudo systemctl enable --now docker
```

### 2. Клонирование проекта

```bash
git clone <REPOSITORY_URL>
cd push-up-tracker
```

### 3. Настройка окружения

```bash
cp .env.example .env
nano .env
```

Пример `.env`:

```dotenv
BOT_TOKEN=YOUR_TELEGRAM_BOT_TOKEN
GEMINI_API_KEY=YOUR_GEMINI_API_KEY
GEMINI_MODEL=gemini-3.5-flash-lite

REPORT_TIMEZONE=Europe/Moscow
DAILY_TARGET=100
CASH_FINE=1000000
DB_PATH=./data/pushups.sqlite3

OWNER_ID=123456789
ALLOWED_CHAT_IDS=-1001234567890
ALLOWED_USER_IDS=111111111,222222222
```

| Переменная | Назначение |
|---|---|
| `BOT_TOKEN` | Токен Telegram-бота (обязателен) |
| `GEMINI_API_KEY` | API-ключ Gemini для анализа видео (обязателен для автоматического подсчёта) |
| `GEMINI_MODEL` | Модель для **групповых** кружочков; по умолчанию в `vision.py` — `gemini-3.5-flash-lite` |
| `REPORT_TIMEZONE` | Часовой пояс отчёта; по умолчанию `Europe/Zurich` |
| `DAILY_TARGET` | Базовая дневная норма; по умолчанию `100` |
| `CASH_FINE` | Денежный штраф, подставляемый в текст правил; по умолчанию `500` |
| `DB_PATH` | Файл SQLite; по умолчанию `./data/pushups.sqlite3` |
| `OWNER_ID` | Telegram User ID владельца (обязателен) |
| `ALLOWED_CHAT_IDS` | ID разрешённых групп через запятую |
| `ALLOWED_USER_IDS` | ID пользователей, которым разрешена личка с ботом, через запятую |
| `RULES_PATH` | Необязательный путь к `rules.txt`; по умолчанию файл рядом с `bot.py` |

Владелец (`OWNER_ID`) автоматически имеет доступ к личным сообщениям бота. Для личного debug используется отдельная константа в `bot.py`:

```python
DEBUG_GEMINI_MODEL = "gemini-3.5-flash-lite"
```

Она передаётся в `analyze_video(..., model_override=DEBUG_GEMINI_MODEL)` и **не зависит от `GEMINI_MODEL`** в `.env`.

Не добавляйте `.env` в Git и убедитесь, что ключ Gemini доступен внутри контейнера.

### 4. Запуск

```bash
sudo docker compose up -d --build
```

Просмотр логов:

```bash
sudo docker compose logs -f bot
```

### 5. Настройка Telegram

1. Создайте бота через [@BotFather](https://t.me/BotFather).
2. При необходимости отключите Privacy Mode: `/setprivacy` → `Disable`, чтобы бот получал обычные сообщения в группе.
3. Разрешите группу через `ALLOWED_CHAT_IDS` или команду `/allowgroup` в личке владельца.
4. Добавьте бота в разрешённую группу.
5. Отправьте `/start`.

Бот покидает группы, которых нет в белом списке.

## Команды бота

### Основные

| Команда | Описание |
|---|---|
| `/start`, `/help` | Информация о боте; в группе также регистрация чата |
| `/stats` | Итоги за сегодня в текущем чате |
| `/yesterday` | Итоги за вчера в текущем чате |
| `/rules`, `/pravila` | Правила челленджа из `rules.txt` |
| `/myid` | Показать свой Telegram User ID (в личке) |

### Управление доступом

Эти команды доступны только владельцу (`OWNER_ID`) в личном чате с ботом.

| Команда | Описание |
|---|---|
| `/allowgroup <chat_id>` | Разрешить группу |
| `/denygroup <chat_id>` | Запретить группу и попытаться выйти из неё |
| `/allowuser <user_id>` | Разрешить пользователю личные сообщения боту |
| `/denyuser <user_id>` | Запретить пользователю личные сообщения боту |
| `/access` | Показать текущие белые списки |

Изменения доступа сохраняются в SQLite, действуют без перезапуска и имеют приоритет над исходными списками из `.env`.

### Ручная корректировка результатов

Команды доступны **только владельцу** (`OWNER_ID`). Они задают итог отжиманий **за выбранный день**, а не число повторений в отдельном видео.

**Ответом на сообщение участника в группе:**

```text
/setpushups 150
/setpushups 150 2026-11-07
/clearpushups
/clearpushups 2026-11-07
```

**В группе, по ID пользователя:**

```text
/setpushups 123456789 150
/setpushups 123456789 150 2026-11-07
/clearpushups 123456789
/clearpushups 123456789 2026-11-07
```

**В личке владельца, с указанием группы и пользователя:**

```text
/setpushups -1001234567890 123456789 150
/setpushups -1001234567890 123456789 150 2026-11-07
/clearpushups -1001234567890 123456789
/clearpushups -1001234567890 123456789 2026-11-07
```

Если дата не указана, используется **сегодня** по `REPORT_TIMEZONE`. Для `/setpushups` допустимо целое число от `0` до `100000`.

Принцип работы корректировок:

- `/setpushups` **заменяет итог за день** указанным значением. Например, если по видео было 90 отжиманий, `/setpushups 150` установит итог **150**, а не 240.
- `/clearpushups` удаляет корректировку; снова используется сумма результатов видеокружочков за день.
- Корректировка сохраняется в таблице `daily_overrides`, исходные записи видео не удаляются.
- В `/stats` и `/yesterday` скорректированный итог помечается 🛠️; расчёт штрафной нормы учитывает такие изменения, в том числе за прошлые дни.
- Корректировка действует на дневной итог, даже если позже за тот же день добавлены новые видеозаписи, пока её не удалят.
- Уже отправленные ежедневные отчёты автоматически не пересылаются.

Для изменения результата через личку группа должна быть зарегистрирована в SQLite. Если участник ещё неизвестен базе, бот попытается получить его данные из Telegram; проще всего использовать команду ответом на сообщение участника в группе.

## Правила челленджа

Текст правил хранится в `rules.txt`. Поддерживаются подстановки:

| Переменная в `rules.txt` | Значение |
|---|---|
| `{DAILY_TARGET}` | Базовая дневная норма |
| `{PENALTY_TARGET}` | Штрафная дневная норма (`DAILY_TARGET × 2 + 10`) |
| `{REPORT_TIMEZONE}` | Часовой пояс отчёта |
| `{CASH_FINE}` | Денежный штраф из `.env` |

Пример `rules.txt`:

```text
🏋️ Правила челленджа

🎯 Ежедневная норма: {DAILY_TARGET} отжиманий.
🚨 Штрафная норма: {PENALTY_TARGET} отжиманий.
💰 Денежный штраф: {CASH_FINE}.
🕛 Отчёт каждый день в 00:00 ({REPORT_TIMEZONE}).
```

Файл перечитывается при каждом вызове `/rules`. Изменения не требуют перезапуска, если обновлённый файл доступен внутри контейнера.

## Принцип работы

1. Участник отправляет `video_note` в разрешённую группу.
2. Бот скачивает MP4 (локальный предел — **20 МБ**) и передаёт его в **Gemini Video API**.
3. Модель ищет наблюдаемые циклы движения корпуса и возвращает JSON:

   ```json
   {"count": 3, "completed_at_seconds": [2.4, 4.1, 6.3], "uncertain": false}
   ```

4. `vision.py` проверяет типы данных, диапазон значений, совпадение `count` с длиной списка временных меток, их порядок и соответствие длительности видео.
5. Если ответ невалиден, запрос завершился ошибкой или `uncertain=true`, бот просит автора указать количество вручную (от **0 до 1000**). Такой результат помечается ✍️.
6. Подтверждённый результат сохраняется в SQLite с привязкой к чату, пользователю, сообщению и времени публикации. Один кружочек не записывается дважды.
7. В **00:00** по `REPORT_TIMEZONE` публикуется отчёт за прошедший день.
8. Если участник не выполнил действующую норму, на следующие сутки назначается `DAILY_TARGET × 2 + 10` (при норме 100 — **210**). Штраф не накапливается: при следующем невыполнении цель остаётся 210. После выполнения действующей нормы цель возвращается к обычной.

**Критерии подсчёта:** промпт намеренно допускает частичные, неглубокие и «грязные» отжимания, минимальные движения корпуса и фронтальный ракурс. Gemini не должен придумывать невидимые повторы, но точность всё равно зависит от видеозаписи и модели. Это подсчёт наблюдаемых движений, а не оценка спортивной техники.

### Частота выборки видео

В текущем `vision.py`:

```python
def analyze_video(path, target_fps=5, *, duration_seconds=None, model_override=None):
    ...
    fps = max(2, min(int(target_fps), 8))
```

По умолчанию запрашивается **5 FPS**; допустимый диапазон после ограничения — **2–8 FPS**. Изменять его нужно в вызове `analyze_video()` или в значении по умолчанию в `vision.py`. Отдельной переменной `.env` для FPS в текущем коде нет.

### Debug-режим в личке

Пользователь из `ALLOWED_USER_IDS` либо владелец может отправить видеокружочек боту в личные сообщения. Для этого используется **`gemini-3.5-flash-lite`**, независимо от модели, выбранной для групп.

Диагностическое сообщение включает, если соответствующие данные доступны:

- Длительность видео, размер файла и локальный предел 20 МБ.
- Время ожидания слота, скачивания, анализа и общее время обработки.
- Количество найденных отжиманий и моменты завершения повторений (timestamps).
- Флаг неопределённости (`uncertain`).
- Запрошенную частоту выборки видео (FPS) и время вызова Gemini API.
- Входные, выходные, thinking-, кешированные и общие токены из `usage_metadata`.
- Использованную модель и `finish_reason` ответа.
- Сведения об ошибке при сбое скачивания или анализа.

Debug-результаты **не записываются в статистику**, и при неудачном распознавании ручной ввод в личке не запрашивается. Лимит одновременных обработок — **2**; время ожидания слота отображается отдельно. Для скачивания используется таймаут **90 секунд**.

## Хранение данных

SQLite хранит следующие данные:

| Таблица | Назначение |
|---|---|
| `chats` | Зарегистрированные группы |
| `members` | Участники и их отображаемые имена |
| `video_counts` | Результаты каждого кружочка; поле `is_manual` помечает ручной ввод |
| `pending_manual` | Кружочки, для которых ожидается ручной ввод |
| `daily_overrides` | Ручные корректировки дневных итогов, дата и ID владельца, внёсшего изменение |
| `access_rules` | Изменения белых списков |
| `reports` | Отметки об отправленных отчётах |

Недостающие таблицы и колонка `is_manual` создаются автоматически при старте. Существующую базу удалять не нужно.

Путь задаётся через `DB_PATH`. **SQLite-файл и сопутствующие WAL/SHM-файлы должны находиться на постоянном Docker volume**, иначе при пересоздании контейнера данные могут быть потеряны. Для резервного копирования работающей базы используйте согласованный SQLite backup, а не слепое копирование только основного `.sqlite3` при активном WAL.

## Обновление с минимальным downtime

Обновить исходный код:

```bash
git pull --ff-only
```

Собрать новый образ без остановки текущего контейнера:

```bash
sudo docker compose build bot
```

Пересоздать только бот:

```bash
sudo docker compose up -d --no-deps --force-recreate --no-build bot
```

Проверить состояние:

```bash
sudo docker compose ps
sudo docker compose logs -f --tail=100 bot
```

Кратковременный перерыв возможен во время пересоздания контейнера. **Одновременно должен работать только один экземпляр бота с Telegram long polling.**
